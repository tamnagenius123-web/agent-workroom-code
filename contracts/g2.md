## Data and authority

Fixed room room_main remains the only product room. New IDs are server UUIDs. Threads have room, immutable title (nonblank UTF-8 <=256 bytes), creator and creation time. A message may belong to one thread; an optional reply target must already be a message in that same thread and room. Room-level messages remain supported; reply without thread is invalid. Links are immutable. Cross-room/thread links reject, including at SQL constraints/triggers. No move/delete endpoint.

Original message text is immutable version 1. Revisions are append-only rows with monotonically increasing message-local version, editor, text/format/time. Only the original author who is still an active write member may revise. Revision requires expected_version >=1 and explicit key. Two competing expected_version=N writes with different keys yield one version N+1, one VERSION_CONFLICT (HTTP409/CLI5), with current_version and history lookup. Same key/content returns its original result even after later revisions; different input conflicts. Reads show current text/version, history shows original plus every revision. Stored operation results remain historical, never silently rewritten.

New schema-only migration 0002 adds threads, immutable links/revisions, current/history views, immutable event feed, opaque cursor/receipt metadata, inbox checkpoint and G2 audit. No existing G1 migration is edited and no seed/backfill is embedded in migration. Events begin when 0002 is applied: new thread/message/revision events only. Retained pre-G2 messages remain available to read/history/export, not retroactively marked new inbox deliveries. Fixture loading is separate. Initial posts continue G1 atomic message/audit/operation semantics; G2 events are inserted by transaction-local triggers. Thread create/revise/ack atomically store operation, effect and G2 audit.

## Inbox and cursor semantics

All newly issued pagination tokens, including room reads, are opaque server-stored UUIDs bound to authenticated principal, room, kind and scope. Old G1 base64 cursors are invalidated; no external clients are connected. Malformed token ->400; valid-shaped missing/other-principal/scope token ->403 without existence detail. Tokens convey continuation only, never authority; every request rechecks current membership. Tokens cannot be edited into arbitrary offsets.

Inbox pull is read/delivery only: execution_accepted=false and processing_complete=false. A first pull starts after that actor's acknowledged checkpoint and freezes the current event watermark. Pages are ascending immutable event IDs/sequence with original event revision content; subsequent pages retain the watermark. Repeating an unacknowledged request can return duplicates with identical event IDs. No pull changes acknowledgement. There is no automatic agent wake-up.

Each nonempty returned page gets an opaque inbox receipt bound to actor/room, exact from/to sequence and watermark. Explicit ack requires that receipt plus its own mutation key. Receipt.from_seq must be <= the actor's current acknowledged sequence; otherwise ACK_OUT_OF_ORDER/409. Thus fetching page 2 without acknowledging page 1 does not authorize skipping page 1. Acknowledgement is monotonic; old/duplicate receipts cannot regress it. Ack reports receipt acceptance/receipt end, not agent execution or a claim of global completion. No caller-supplied numeric offset/event ID/actor is accepted. Other-actor and invented receipts reject. Empty pages have no receipt. Cursor/receipt issuance is read metadata, not a business mutation; it does not create audit success, message changes or ack. Each call persists only a bounded number of such records. G2 retains metadata; retention/cleanup is a later operational decision.

Pre-implementation independent review clarification: receipt.from_seq is the exclusive lower bound (initial acknowledged checkpoint, then prior page end); to_seq is the inclusive last returned event. First receipt from_seq=0 permits the initial ack; page 2 from_seq equals page 1 to_seq. Existing G1 stored operation responses without version/thread fields remain accepted by output schemas. Export captures max-message sequence and revision-event watermark together in one SQL statement/snapshot, and applies both to the first and every later page. Reviewer read the specification only, not runtime validation.

## Export and bounds

Page export emits authorized workroom history only: source_message_id, source_revision, source_thread_id/reply target, original author/editor, time, original format/text and explicit query range. It reads no filesystem, env secrets, private plan or research source. No automatic private input attachment. Optional thread filter is validated in this room. Export includes all retained revisions, including original version 1. First page freezes max message sequence and revision-event watermark; later revisions/new messages do not change that export. Position is (message sequence, revision version). Cursor binds actor/room/thread/output format/snapshot.

Export format text or markdown, default text; JSON envelope always includes structured records plus rendered text. Markdown bodies are fenced using a fence longer than any backtick run, so HTML/images/links remain literal. UI uses textContent for messages/export. Default export page 10/max20 history rows; read/history/inbox default50/max100; text <=32KiB and request body <=48KiB remain. New mutations share 60/principal/UTC-minute quota and explicit key/hash/recovery. No hidden mutation retries. Output/query work is bounded per page. Snapshot consistency across independently started exports is not promised.

## Interfaces (all REST paths under /api/v1)

| CLI | REST | MCP |
|---|---|---|
| thread create --room R --title T --idempotency-key K | POST /rooms/R/threads | workroom_thread_create |
| thread read --room R --thread T [--cursor C --limit N] | GET /rooms/R/threads/T | workroom_thread_read |
| message post ... [--thread T --reply-to M] | existing POST /rooms/R/messages | existing workroom_message_post |
| message revise --room R --message M --expected-version N (--stdin or --file P) --idempotency-key K | POST /rooms/R/messages/M/revisions | workroom_message_revise |
| message history --room R --message M [--cursor C --limit N] | GET /rooms/R/messages/M/history | workroom_message_history |
| inbox pull --room R [--cursor C --limit N] | GET /rooms/R/inbox | workroom_inbox_pull |
| inbox ack --room R --receipt T --idempotency-key K | POST /rooms/R/inbox/ack | workroom_inbox_ack |
| room export --room R [--thread T --export-format text/markdown --cursor C --limit N] | GET /rooms/R/export | workroom_room_export |

Existing operation get supports message.post, thread.create, message.revise and inbox.ack; key scope remains principal+operation+key. Every payload has schema_version=1; strict request schemas reject identity/unknown fields. Post optional JSON fields are thread_id/reply_to_message_id. G1 post canonical hash is preserved when neither field is supplied. Thread-create JSON: title; revise JSON: expected_version,text,format; ack JSON: receipt. REST Idempotency-Key maps to MCP idempotency_key and CLI --idempotency-key. Path fields map to room/thread_id/message_id tool fields. Existing response envelope, request IDs, unknown outcome and exit codes remain. CLI validates command-specific outputs, HTTP/body success agreement and operation keys, preserving the G1 fix.
