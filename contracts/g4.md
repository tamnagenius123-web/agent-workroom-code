## Identity and authorization design

Intended deployment is one private central server, not server copies on each bot. G4 introduces a provider-neutral *probe gateway factory* and trusted verification interfaces; it is not wired into the production worker, existing REST/CLI or existing19-tool MCP. Without a configured verifier, current binding resolver, audit sink and trusted endpoint config, gateway default-denies. There is no production verifier in this slice. Header/body actor names, clientInfo, OAuth user identity, agent display names, service tokens and approval booleans are not interchangeable authority.

Only a trusted provider verifier may return an assertion. It must verify cryptography or authenticated ingress provenance, issuer/subject, credential audience and revocation before returning; parsing caller JSON/JWT/header values without verification is prohibited. G4 revalidates assertion structure/lifetime/resource/ingress and current binding policy. Verifier input is request headers/method/url plus server-selected ingress ID; no request body is consumed and no identity is derived by this layer from caller fields. Production verifier missing =>503 AUTH_NOT_CONFIGURED; null/invalid/thrown assertion =>redacted401. No permissive fallback.

Verified assertion fields: issuer, subject, subject_kind(agent/user/service), credential_id, credential_version, audience, ingress_id, issued_at_ms, expires_at_ms and scopes. Binding resolver is trusted operator-side state keyed by issuer+subject+credential_id, never user input. Binding fields repeat that key plus principal_id, kind(agent/user), agent_id(required agent/null user), room_id, audience/ingress_id, active, credential_version, not_before_ms, expires_at_ms, scopes. Service subjects reject even if misbound. Assertion kind must match binding kind; verified site user cannot become an agent. Distinct bots require distinct verified bindings/principals; one shared credential is not three identities. No real binding/grant provisioning interface is provided. Test-only fixtures use separate public synthetic assertions for alpha/beta/human; never real Bot credentials.

Effective permissions are intersection of verified credential scopes, current server binding scopes and current DB principal/membership/role. Assertion credential_version must equal binding.credential_version exactly. Binding active/credential_version/expiry is checked every time, without internal cache. Roles come from principal_roles, not claims; binding kind must match DB kind. Current room is fixed room_main. A user subject may perform read-only probes as user with agent_id=null; it does not prove which assistant made a user-delegated request. Task approval/write scopes are excluded. Rotation increments binding credential_version and rejects the old version; revocation immediately denies the next check, including a post-operation check before emitting data. Test policy max assertion lifetime is5minutes; no operational lifetime/support is asserted. Real issuer/JWKS/introspection/audience/expiry/rotation support remains a later decision. No keys are minted/stored/rotated now.

## Small implemented probe surface

REST under approved same origin: GET /connection/me; POST /connection/echo {schema_version:1,nonce}; POST /connection/readback {schema_version:1,room,message_id,expected_version}. Echo nonce is16–64 ASCII letters/digits/underscore/hyphen, no arbitrary content/URLs. Echo is not persisted. Readback uses existing Workroom/G2 message domain and requires exact current version; returns one authorized saved message with source/version, no pagination or new mutations. Domain membership is checked, then assertion/binding/DB authority rechecked before release with the same principal/agent/kind/credential version. No task/message writes, signup, model/runner call or automatic wake-up.

Separate gateway POST /mcp exposes only workroom_connection_whoami, workroom_connection_echo, workroom_connection_readback. Existing local MCP19 tools remain unchanged. Use official SDK2.3.1 and MCP2026-07-28 discovery/list/call, reject legacy and unsupported/mismatched version framing. No silent version downgrade, stdio server installation or OAuth login. Authentication precedes discovery/list. Each tool also rechecks exact scope and final authority. scopes: connection.identity / connection.echo / room.read. Strict schemas reject actor_id/agent_id/role/identity/scope/time/unknown input. Error bodies and JSON-RPC errors contain fixed codes/messages, never verifier exceptions, credentials, raw headers or upstream response content. SDK result content is untrusted literal data.

Audit callback records only generated request ID, fixed action, allow/deny, fixed reason code and trusted principal_id (or null). No tokens, subjects, issuer-provided error strings, headers, URLs, nonce, message text or raw payloads. Missing audit configuration =>default-deny; audit failure =>redacted503 and no successful data response. G4 audit is an injected synthetic sink, not a claim of durable production audit. There is no new DB migration: current identity provisioning, credential storage and production audit persistence are deliberately not guessed;0001–0003 remain byte-identical.

## HTTPS policy and offline handoff CLI

A reusable outbound fetch guard requires trusted exact canonical HTTPS origin/resource /mcp and an explicitly injected transport. No global fetch fallback: without transport it denies without network. HTTPS default port only, no username/password/query/fragment/encoded path drift/IP/localhost/private-name suffix. All calls must target the exact resource with POST; redirect:error is forced, any3xx/redirected/different response URL rejects without forwarding credentials. Responses must be bounded JSON (<=512KiB), requests<=48KiB; body/transport errors are fixed redacted messages. Tests use an in-process fake transport, no DNS/real HTTPS call. DNS rebinding/private-address resolution, TLS trust, proxies and real egress are not verified by string validation; no production readiness claim. A future real transport requires a verified host/egress/auth contract.

New offline CLI workroom-connection-plan accepts --stdin or --file JSON (<=32KiB), outputs exactly one JSON + stderr diagnostics/exit2 invalid input. Valid plans return exit0 with ready=false,outcome=not_executed and blockers; it never connects, installs, registers, authenticates or changes settings. Unknown/credential fields reject without echoing values. No credential flag/env support. Plan fields identify provider/sites/grok-bot/muse, native-https-mcp, optional endpoint/expected principal/agent, fixed room/protocol, operational_verifier:not_configured. Plan/user inputs never become trusted config. Existing Workroom CLI remains loopback-only and engine>=24.19.0.

handoff/g4 contains provider-specific Markdown prompts and a blank JSON report/example plan. These are files for the user, not sent to agents. Prompts request capability evidence only; no registration/OAuth/credential grant/network changes or real connection until a separate approved endpoint/auth contract exists. No secrets in prompts/command arguments/reports. Native remote registration and local package runtime support are reported separately. No Node20 compatibility claim. No curl credential example.
